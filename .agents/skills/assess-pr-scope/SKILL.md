# PR 범위 판단

## 확인

```bash
git status
git log --reverse --oneline <베이스>..HEAD
git diff --name-only <베이스>..HEAD
git diff --shortstat <베이스>...HEAD
git diff --numstat <베이스>...HEAD
git diff --name-only <직전-경계>..<현재-경계> | wc -l
gh pr list --state all -L 20 --json number,title,headRefName,baseRefName,state
```

- 저장소 규칙과 기존 PR에서 베이스 브랜치를 확인한다.
- 전체 변경과 각 후보 경계에서 파일 수, 추가·삭제 줄 수와 바이너리 파일을 확인한다. 생성물, 이동 파일과 lockfile은 별도로 표시한다.
- 프로젝트가 정한 리뷰 예산이 있으면 우선 적용한다.
- CodeRabbit 같은 자동 리뷰 도구가 있으면 설정과 최근 리뷰 결과에서 현재 provider 제한을 확인한다. 확인할 수 없는 제한은 숫자를 추정하지 않고 미확인으로 남긴다.

## 경계 결정

1. 커밋 하나를 PR 하나로 간주하지 말고 논리적 책임과 사용자 가치에 따라 연속된 커밋 묶음을 만든다.
2. 각 묶음이 직전 경계 위에서 빌드되고 검증 가능하며, 다음 묶음이 의존할 수 있는 순서인지 확인한다.
3. 한 선형 히스토리의 연속 묶음은 직전 head를 base로 쓰는 stacked PR을 기본으로 한다. 공통 base에서 갈라진 head가 이미 있고 서로 의존하지 않을 때만 독립 PR로 분류한다.
4. 각 묶음의 파일 수와 코드량은 기본 브랜치가 아니라 자신의 직전 base와 비교한다.
5. 리뷰 예산이나 확인된 provider 제한을 넘는 묶음은 논리적 경계를 보존하면서 기존 커밋 경계에서 다시 나눈다.
6. 한 커밋이 여러 책임을 섞거나 그 자체로 제한을 넘으면 필요한 커밋 재구성만 보고한다.

파일 수나 코드량은 분리 신호이지 단독 근거가 아니다. 숫자를 맞추기 위해 결합된 책임을 쪼개거나 서로 무관한 책임을 합치지 않는다. 떨어진 커밋을 한 묶음으로 재배열하거나 기존 커밋을 수정하지 않는다.

## 결과

다음 항목을 표로 제시한다.

- 순서와 책임
- 연속된 커밋 범위와 경계 SHA
- 제안 head와 정확한 base
- 직전 base 대비 변경 파일 수와 추가·삭제 줄 수
- 분리 또는 유지 이유
- 선행 PR 의존성
- 추가 커밋 재구성 필요 여부

한 PR로 충분한지, 독립 PR 여러 개인지, stacked PR이 필요한지 함께 결론낸다. 여러 PR을 권하면 게시 전에 사용자가 확인할 수 있는 순서와 경계를 제시한다. 저장소와 GitHub 상태는 변경하지 않는다.
